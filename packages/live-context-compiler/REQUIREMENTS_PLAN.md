# Live Context Compiler — Requirements and Implementation Plan

## 1. Product goal

Build a live repository intelligence service that compiles a task-specific context slice for an LLM from deterministic code relationships.

The system must reduce repeated repository exploration without pretending that summaries replace source code.

## 2. Non-goals for the first version

- Do not support every language.
- Do not use an LLM to generate authoritative dependency edges.
- Do not rely on embeddings to determine relationships.
- Do not attempt perfect whole-program analysis immediately.
- Do not introduce Neo4j until SQLite/PostgreSQL traversal becomes a measured bottleneck.

## 3. MVP scope

Start with TypeScript and JavaScript repositories.

### Required graph nodes

- file
- function
- method
- class
- interface
- type
- API route
- event
- configuration key
- unresolved dynamic target

### Required graph edges

- CONTAINS
- IMPORTS
- CALLS
- REFERENCES
- EXTENDS
- IMPLEMENTS
- EXPOSES_ROUTE
- CONSUMES_ROUTE
- EMITS
- CONSUMES_EVENT
- TESTS
- UNRESOLVED_DYNAMIC

### Required behavior

- Full initial index.
- Content-hash-based incremental index.
- File watcher.
- Stable graph storage.
- Symbol lookup.
- Reverse lookup for callers and consumers.
- Bounded graph traversal.
- Raw source extraction.
- Explicit unresolved dynamic edges.
- Benchmark harness.

## 4. MVP architecture

```text
Repository
  -> file watcher
  -> TypeScript compiler indexer
  -> graph store
  -> deterministic traversal policies
  -> raw-source context renderer
  -> coding agent
```

## 5. Production architecture

```text
Repository watcher
  -> language-specific indexers
  -> deterministic graph builder
  -> contract adapters
  -> data-flow and control-flow layer
  -> runtime trace importer
  -> context compiler
  -> MCP tools
```

### Verified graph

Contains relationships proven by parsers, language servers, compilers, schema adapters, tests, or runtime observations.

### Annotation graph

Contains optional labels, summaries, and candidate entry points generated by a local model or embedding search. These annotations are never authoritative.

## 6. Implementation phases

### Phase 0 — Baseline measurement

Before building more features, record a baseline agent session on 20 tasks:

- token usage
- tool calls
- elapsed time
- files read
- task success
- tests passed

Use the same repository and same tasks for later comparison.

### Phase 1 — Deterministic TypeScript graph

Replace the scaffold's local-only call resolver with the TypeScript Compiler API `Program` and `TypeChecker`.

Deliverables:

- cross-file imports
- aliases
- symbol references
- method calls
- inheritance
- interface implementations
- stable symbol identifiers
- caller and callee queries

Exit gate:

- at least 95% recall for expected symbols on a manually reviewed 50-task gold set
- zero stale edges after save/delete/rename benchmark cases

### Phase 2 — Contract graph

Add framework adapters:

- Express
- Fastify
- NestJS
- Next.js route handlers
- React fetch/Axios clients
- Prisma
- Drizzle
- TypeORM
- raw SQL pattern adapter
- queue/event adapter
- environment variables

Exit gate:

- trace at least 90% of manually labeled frontend -> API -> service -> DB paths in the selected test repository

### Phase 3 — Semantic dependency slicing

Add deterministic task policies:

- function edit
- endpoint edit
- schema edit
- event edit
- backward value slice
- forward impact slice

Add strict budgets:

- maximum hops
- maximum nodes
- maximum files
- maximum raw-source tokens

Exit gate:

- maintain task success within 5 percentage points of baseline agent exploration
- reduce context tokens by at least 50%

### Phase 4 — Live invalidation

Add dirty propagation:

```text
changed file
  -> changed symbols
  -> changed edges
  -> affected relation containers
  -> invalidate cached slices
```

Exit gate:

- p95 incremental update latency under 2 seconds on the target repository
- no stale graph result in mutation tests

### Phase 5 — Runtime-confirmed dynamic edges

Import traces from integration tests and development runs.

Store observed runtime edges separately from static edges:

- OBSERVED_RUNTIME
- OBSERVED_TEST
- UNRESOLVED_DYNAMIC

Do not infer that an unobserved path is impossible.

Exit gate:

- dynamic dispatch cases become traceable without deleting unresolved alternatives

### Phase 6 — Agent interface

Expose MCP tools:

- find_symbols
- get_callers
- get_callees
- get_contract_path
- slice_for_function_edit
- slice_for_endpoint_edit
- slice_for_schema_edit
- slice_for_value
- expand_slice
- get_raw_source
- report_unresolved_edges

Exit gate:

- agent uses graph tools first and reads raw code only after slice compilation

## 7. Testing strategy

### A. Unit tests

Test each extractor independently:

- local function call
- imported function call
- aliased import
- class method call
- interface implementation
- route declaration
- API client call
- event emitter
- event consumer
- DB read
- DB write
- file delete
- file rename
- dynamic call marked unresolved

### B. Mutation tests

For each gold repository fixture:

1. Index repository.
2. Change one function.
3. Confirm old edges are removed.
4. Confirm new edges appear.
5. Confirm affected slices change.
6. Confirm unrelated slices remain unchanged.

### C. Gold retrieval benchmark

Each task should include:

```json
{
  "task": "Add an admin action to disable a user account",
  "entry_candidates": ["disableUser", "PATCH /admin/users/:id/status"],
  "required_nodes": [
    "AdminUserPage",
    "PATCH /admin/users/:id/status",
    "disableUser",
    "users.status",
    "adminAuthorizationMiddleware"
  ],
  "forbidden_nodes": ["invoiceGenerator"],
  "maximum_context_tokens": 20000
}
```

Measure:

- required-node recall
- unrelated-node precision
- edge correctness
- stale-edge rate
- generated context token count
- retrieval latency

### D. Agent A/B benchmark

Run the same real coding tasks in two modes:

1. Baseline: normal grep, file reads, and agent exploration.
2. Graph-first: deterministic slice, then targeted expansion.

Measure:

- final tests passed
- human review score
- tokens consumed
- tool calls
- files read
- elapsed time
- regressions introduced

### E. Scale benchmark

Generate synthetic repositories with repeated but linked modules:

- 10k LOC
- 100k LOC
- 1M LOC

Measure:

- initial index time
- index database size
- p50/p95 incremental update latency
- p50/p95 slice latency
- memory usage

## 8. Decision gates

Do not add embeddings until deterministic retrieval has been measured.

Add embeddings only if natural-language entry-point discovery is a real bottleneck.

Do not add a graph database until SQLite or PostgreSQL traversal is proven insufficient by benchmark.

Do not add a model-generated graph. Use a model only for optional summaries and entry-point suggestions.
